### `bp` 模板為什麼只有 `BP` 兩個字,沒有後面的冒號

原本的 `bp.png` 寬 64px,包含 `BP` 之後的全角 `：`——因為當初取樣的客戶端有畫。
後來客戶端把冒號拿掉、間距也縮緊了,於是模板約 1/3 的面積落在**累計 BP 的第一位數字**上,
一個每場都會變的字元。真標籤分數從 0.955～1.000 掉到 **0.706～0.727**,而門檻是 0.7。

沒有任何東西會報這件事:`score_system` 不在 `reading.rs` 的 `watched` 三人組
(`result` / `resultMid` / `modesCPU`)裡,而 `noteScore` 的 near-miss 只記錄**低於**門檻的分數
——「剛好高過門檻 0.006」在遙測上完全隱形。代價是連續三場(`Match` id 352／353／354)
同時掉了模式與 BP,只留下 `mode-guessed` 與 `ranked-no-numbers`。

模板改切到 `P` 為止(40×28)之後,冒號與數字都被排除,同一個模板同時吃新舊兩版客戶端
(上表的「勝」「敗」兩列是舊版素材,仍有 0.976／0.955)。素材見
`tests/fixtures/captures/ranked-bp-1920-windowed-no-colon/`。

**代價要說清楚**:2Pick 結算畫面自己的「BP 100」誤判從 0.757～0.787 升到 0.948～0.963。
它本來就已經超過 0.7,所以行為性質沒變,但這個設計原本倚賴的邊際沒了——
現在完全靠 `TWO_PICK_VERSUS_OWN` 維持 authoritative 才不會把 2Pick 判成階級
(詳見 `Machine::ranked` 的註解)。非 BP 也非 2Pick 的畫面在所有素材上最高 0.595。

### 標籤視窗必須是「錨點」,不能是兩個固定小窗(既有 bug,已於本次修正)

上表最後一列的「BP 版面 / 敗」是後來補上的
(`tests/fixtures/captures/ranked-bp-1280-windowed-lose`,1280×720 視窗化)。它揭露了
一個原本看不見的缺陷:**結算畫面的獎勵清單行數不固定**。

- 勝利:對戰勝利 ＋ 對戰表現獎勵 ＋ 3 條子項 ＋ TOTAL = 6 行
- 敗北:對戰表現獎勵 ＋ 時間獎勵 ＋ TOTAL = 3 行

清單下方的「階級／BP」整塊會跟著上移 **3 × 33 = 99px**(實測 `bp` 標籤 y=420 → y=321)。

原本的 `scoreSystemCr (990,275,150,85)` / `scoreSystemBp (1020,390,160,90)` 是照勝利版面
各切一個小窗,於是敗北畫面上:

1. `bp` 掉出 `scoreSystemBp` 之外;
2. 反而落進 `scoreSystemCr` 裡,但那裡只認 `cr` 這個名字,因此被丟棄;
3. `detectScoreSystem` 兩邊皆未命中 → 回傳 null → **整場階級對戰從未被判定為 ranked**。

這也是使用者回報「1280×720 視窗化認不出模式」的真正原因 —— 與解析度無關,
同一段錄影裡 classes / emblems / playOrder / result 全都 0.9+ 正常命中。

修正方式:改為單一高視窗 `ROI.scoreSystemAnchor (990,230,250,250)`,兩個模板在同一個窗內
競爭,勝者過門檻即採用;再以 `resultLayoutOffset()` 算出相對於基準版面的垂直位移,
把所有數值 ROI 一起平移(`shiftRoi`)。

視窗尺寸的依據:

- **高度**涵蓋兩種版面 + 比目前觀察到更長的獎勵清單。
- **寬度**涵蓋 count-up 動畫期間標籤的水平飄移(實測 1053 → 1105)。但**位移只取垂直分量** ——
  獎勵清單是靠右對齊到固定欄位的,不會跟著標籤橫移。
- **區隔仍然乾淨**:真標籤 0.955–1.000;整段 110 秒錄影 + CPU 練習素材裡最差的誤命中是
  **0.467**,門檻 0.7 落在中間。

連帶修掉的第二顆雷:即使模式判對,未平移的 BP 視窗 `(1150,334,90,32)` 在敗北畫面上切到的是
下面那行 `BP:88794`(累計總分),OCR 讀出 `"077"` —— **不是空字串**,是會被當成本場得分寫進
資料庫的錯誤數字。`pnpm vision:check-ocr-numbers` 現在同時斷言「平移後讀到 `+8`」與
「未平移時讀到的不是 `+8`」。

MP 版面沒有獎勵清單,兩張 fixture 的位移實測皆為 0,因此其四個數值 ROI 維持原值。

MP 版面的四個數值 ROI 已校準並逐一驗證(`binarizeRoiToPng` 產出的正是 Tesseract 收到的圖):

| 數值    | ROI              | 敗      | 勝      |
| ------- | ---------------- | ------- | ------- |
| 獲得MP  | (1126,175,52,28) | `+15`   | `+173`  |
| MP 總量 | (1142,212,90,32) | `41743` | `41938` |
| 變動CR  | (1176,305,46,28) | `-16`   | `+14`   |
| CR 總量 | (1162,340,68,30) | `1557`  | `1538`  |

**2. 標題列偵測原本是壞的(既有 bug)**

這是兩張截圖帶來的更大收穫。它們是視窗擷取(長寬比 1.6923,非 16:9),會走
`detect_title_bar_height` 與 letterbox 裁切 —— 而該函式原本的註解寫著
「視窗擷取會有**深色**標題列」,邏輯是往下找第一個「不夠暗或不平坦」的列。

實測這張擷取的前 32 列:

```text
row  0      mean 112  sd 0.00   邊框
rows 1-2    mean 219  sd 0.00   邊框
row  3      mean  64  sd 0.00   邊框
rows 4-30   mean 255  sd 0.00   標題列(純白)
row  31+    mean  55  sd 11.5   遊戲內容
```

平坦帶的亮度橫跨 64–255。淺色主題下 row 0(mean 112)就滿足 `mean >= 80`,函式立刻回傳 0,
**整條標題列留在畫面裡,所有 ROI 因此下移約 30px**。而 ROI 餘裕只有 ±20px,
等於在視窗模式下所有偵測都會失效 —— 而且是靜默失效。

修正:判準改為**只看紋理、完全不看亮度**,並要求紋理**連續 4 列**才算內容起點。
第二個條件同樣是實測逼出來的:另一張截圖的 row 0 有 sd 9.9(視窗邊緣混到桌面),
只看單一列會在 row 0 就停下,又變成什麼都不裁。

順帶說明:現有 BP/CR 的 OCR ROI 看起來剛好比實際位置低約 30px,推測是當初在
「標題列 bug 生效中」的視窗擷取上校準的,因此把偏移編碼進了座標。這些 ROI 已隨本次一併重新校準。

### `modes_ranked` 的 ROI 是錯的(既有 bug,已於本次修正)

現有程式碼在 `rankDetectArea = (780, 205, 150, 60)` 找 rank 徽章,但全片掃描顯示
該徽章實際出現在 **(74, 283)**,分數 **0.9021**,時間點是**開戰前的首頁畫面**(錄影 6–32 秒)。
`rank.png` 是首頁「階級對戰」選單按鈕上的金色徽章,而 (780,205) 在結算畫面上是戰後統計文字面板。

後果:`rankDetect.score > 0.7` 永遠不成立,因此**階級對戰的 mode、CR、ΔCR、BP 全都不會被寫入**。
結算畫面上這些數字確實存在(已目視確認 +100 / +24 / +124 / BP 89620),
所以只要把閘門修好就能解鎖。

**修正方式**:改用 `detectScoreSystem()` 當閘門,不再依賴徽章。
BP / MP 標籤就在**要讀取數值的同一個畫面上**,而且它還多回答了一個必要問題 ——
是哪一套積分制度、因此數值在哪裡。徽章方案兩者都做不到。

殘留的 `modes_ranked` 模板與 ROI 目前已無人使用(仍會被載入與搜尋),
要刪除或改用真實位置 (74,283) 當「開戰前的階級提示」,已另開任務追蹤。

## 3. 效能實測

單幀跑完現有全部搜尋範圍(直接法 NCC,已用 rayon 跨核平行):

| 搜尋                        | 耗時         |
| --------------------------- | ------------ |
| resultMid 全屏              | 2,100ms      |
| result 全屏                 | 780ms        |
| emblems 左+右               | 1,360ms      |
| classes 左+右               | 670ms        |
| playOrder 左+右             | 445ms        |
| history 全屏                | 253ms        |
| modesCPU ×3                 | 152ms        |
| custom 左+右                | 120ms        |
| **modesRanked ROI(已收緊)** | **0.4ms**    |
| **modes2Pick ROI(已收緊)**  | **0.4ms**    |
| 合計                        | **~5,700ms** |

分析器的 tick 週期是 500ms,所以現有的寬範圍搜尋在直接法下超出預算約 11 倍。

關鍵對照:**已經收緊 ROI 的兩個搜尋只花 0.4ms**,而結構完全相同、只是搜尋範圍是半屏/全屏的搜尋要 250–2,100ms — 差距達三到四個數量級。成本幾乎完全由候選位置數量決定,而非演算法。

### 效能:核心數是關鍵變數

**最重要的一課**:最初在這台 32 核機器上量到「單 tick 327ms,佔預算 65%」,看起來很安全。
但用 `RAYON_NUM_THREADS` 模擬較少核心後才發現那是假象 —— 比對成本幾乎與核心數成反比:

| 邏輯核心 | 寬範圍搜尋 | 收緊 ROI 後 | 再加半解析度比對 | 佔 500ms 預算 |
| -------- | ---------- | ----------- | ---------------- | ------------- |
| 32       | 327ms      | 173ms       | **65ms**         | 13%           |
| 16       | 438ms      | 245ms       | **74ms**         | 15%           |
| 8        | 746ms ❌   | 405ms       | **100ms**        | 20%           |
| 4        | 1,356ms ❌ | 707ms ❌    | **160ms**        | 32%           |
| 2        | 2,521ms ❌ | 1,290ms ❌  | **269ms**        | 54%           |
| 1        | —          | 2,185ms ❌  | **473ms**        | 95%           |

原始實作在 **8 核以下就會超支**(而 8 核是很普遍的配置)。兩階段優化後連單核都能落在預算內。

量測方式(`RAYON_NUM_THREADS` 可調整可用核心數):

```bash
node tools/vision-node-addon/bench-tick.cjs <frame.png> [...] --iterations 8
```

量測時務必確認沒有殘留的 electron / capture-tool 行程 —— 它們會讓數字虛高一倍以上。

### 第一階段:收緊 ROI 的實測結果

用 `tools/vision-node-addon/verify.cjs` 透過實際的 Node addon,在同一批畫面上對照
寬範圍與校準後 ROI(8 幀:6 張 fixture PNG + versus 畫面 + 先後攻提示):

```bash
node tools/vision-node-addon/verify.cjs <frame.png> [...]
```

| 搜尋                     | 寬範圍      | 收緊 ROI      | 加速      |
| ------------------------ | ----------- | ------------- | --------- |
| classes 左 / 右          | 311 / 318ms | 14.0 / 16.3ms | 22x / 19x |
| emblems 左 / 右          | 614 / 617ms | 25.4 / 33.9ms | 24x / 18x |
| playOrder 左 / 右        | 215 / 214ms | 11.8 / 10.8ms | 18x / 20x |
| modesCPU(兩處位置取最大) | 116ms       | 5.2ms         | 22x       |
| resultMid                | 2,129ms     | 80.6ms        | 26x       |
| result                   | 783ms       | 26.5ms        | 30x       |
| **單幀合計**             | **5,226ms** | **219ms**     | **23.9x** |

加上載入與正規化(約 30ms),每 tick 約 **250ms**,佔 500ms 預算的一半。

驗證腳本同時比對兩者的判定結果:**8 幀中所有寬範圍的強匹配(score ≥ 0.7)都被收緊 ROI 完整重現**
(模板名稱相同、分數差 < 1e-9)。

尚未校準的 `history`/`custom`/`modesPlaza` 若維持現狀會再加約 400ms;這三者都是狀態指示器,
採**降頻攤平**(例如每 4 個 tick 檢查一次)後約 100ms,總計約 350ms,仍在預算內。

ROI 是由**測到的元素中心**推導,而非手調:尺寸 = 該集合最大模板尺寸 + 2×20px 餘裕。
這是能容納集合內所有模板(各職業尺寸不同,左上角會位移)又能吸收實測漂移(最多 6px)的最小視窗。
餘裕是主要的效能旋鈕 —— 每放寬 20px,工作量約加倍。

### 第二階段:大模板改用半解析度比對

收緊 ROI 後,成本集中在兩個「大模板 × 大視窗」的搜尋上(8 核實測):
`history` 佔整個 tick 的 47%、`result_mid` 佔 28%,其餘 11 項合計才 18%。

比對成本同時與候選位置數**和模板面積**成正比,所以解析度砍半 ≈ 工作量降到 1/16。
`history` / `result_mid` / `result` 因此改用 ×2 比對。

**這一步必須驗證,不能想當然**。`tools/vision-node-addon/check-scales.cjs` 拿已知的
正例與反例逐一比對各 scale 的分數:

| 案例                              | ×1     | ×2     | ×4            |
| --------------------------------- | ------ | ------ | ------------- |
| `05-game-set` gameset(需 ≥0.7)    | 0.8813 | 0.9188 | 0.9218        |
| `06-result` lose(需 ≥0.7)         | 0.9410 | 0.9486 | 0.8590        |
| `06-result` cpu(需 ≥0.58)         | 0.9287 | 0.9367 | 0.7068        |
| `02-cpu-deck-label` cpu(需 ≥0.58) | 0.6085 | 0.6062 | **0.5475 ❌** |
| `01-home` result(需 <0.7)         | 0.1132 | 0.1166 | 0.1300        |
| `01-home` cpu(需 <0.58)           | 0.1362 | 0.1593 | 0.2037        |
| `04-battle` result_mid(需 <0.7)   | 0.0782 | 0.0817 | 0.0914        |

×2 對全部案例都安全(分數多半還略升),但 **×4 會讓開戰前的 CPU 偵測跌破門檻** ——
若當初直接採用 ×4,就會靜默破壞 fixture README 明載的預期行為之一,而且症狀是
「偶爾抓不到 CPU 模式」這種極難追查的間歇性 bug。因此 ×4 不使用。

因為 `history` 變便宜了,它的檢查頻率**維持每 4 個 tick**而非拉長 —— 這點很重要:
該偵測是用來抑制「把重播誤記成對戰」的,間隔拉長會擴大誤記窗口。

### 重要發現:同一模板可能有多個固定位置

`modes_cpu` 在**開戰前畫面**位於 (1142, 101),在**結算畫面**位於 (694, 245)。
寬範圍搜尋會同時涵蓋兩者,收緊後必須**兩個 ROI 都查、取最大值**
(現有 TS 的 `bestMatch(...)` 已是這個模式)。

這是驗證腳本抓到的 — 一開始只設了開戰前的 ROI,結算畫面的分數就從 0.9287 掉到 0.2625。
收緊任何 ROI 之前,都應該先確認該元素是否在不同畫面有不同位置。

## 4. 結論:不需要 FFT

FFT 的成本由**填零後的區域尺寸**決定,而不是候選位置數量,所以收緊 ROI 對 FFT 幫助有限;
反之直接法的成本與候選位置數成正比,收緊 ROI 直接得到數十倍改善。

在本專案的條件下(畫面已正規化成固定 1280×720、UI 元素位置固定、模板多為小圖示),
**直接法 NCC + 固定 ROI + 大模板降採樣** 同時在效能與可維護性上都優於 FFT 方案:

- 效能:實測 65ms(32 核)/ 100ms(8 核)/ 473ms(單核),對比 FFT 方案估算的
  11–12 GFLOP/tick(約 1 秒以上,且 FFT 成本由填零區域決定,收緊 ROI 幫助有限)
- 可維護性:約 60 行直觀算術 + 一個 box-average 降採樣函式,不必處理 FFT 的填零長度、
  circular wraparound、實數 FFT 正規化係數等數值陷阱
- 若未來還需要更多餘裕,SIMD(5–10 倍)這張牌尚未打出

## 5. 已知限制

- 只有**一種解析度/視窗模式**(1920×1080 全螢幕)。此模式長寬比恰等於 16:9,`detect_title_bar_height`
  會直接回傳 0,因此**標題列偵測與 letterbox 裁切這兩條路徑尚未被驗證**。需要 1280 視窗、1920 視窗的素材。
- 只有**一種對戰組合**(witch vs bishop)。同類別的模板尺寸不一(classes 67–138 寬、emblems 61–92 寬),
  不同職業的左上角命中座標會隨模板尺寸位移,因此 ROI 邊界需保留足夠餘裕,並建議再用其他職業的對戰驗證。
- 只有**一種模式**(CPU 練習)。ranked 的 CR/BP OCR 路徑、2pick、plaza、custom、history 都未驗證。
- 先後攻提示只顯示約 0.9 秒,而 tick 週期是 500ms — 這是既有的時序脆弱點(與本次改動無關),
  若某次 tick 耗時偏長就可能整場漏掉。

所以兩者仍可能漂移,這不能取代實跑 App。

### 6.1 已驗證的兩段錄影

| 錄影                                                                       | 結果                                                             |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `tests/fixtures/captures/cpu-practice-1920-fullscreen/recording.mp4`(1:29) | witch vs bishop / 後攻 / cpu / 敗北 — 與 fixture README 記載一致 |

1564 格沒有任何一格超過 500ms 預算。

### 6.2 重播找到的兩個既有缺陷

**1. ranked BP 的 OCR 視窗完全落在數字之外。**
原本是 `{ x: 1115, y: 200, w: 65, h: 30 }`,位置落在「對戰表現獎勵」標籤與其數值之間的
空白處,實測在整段錄影的每一格都讀回空字串——**ranked 的 `bp` 從來沒有被記錄過**。
之所以一直沒被發現,是因為 ranked 分支原本由壞掉的 `modes_ranked` 探測把關,這段程式
一次都沒執行過;把把關換成 `detectScoreSystem()` 之後才第一次跑到。

改為 TOTAL 那一列 `{ x: 1150, y: 334, w: 90, h: 32 }`(即該場實際獲得的 BP),
在 fixture 與錄影的每一格都穩定讀出 `+124`。游標偵測視窗也一併移到新位置——
游標視窗必須覆蓋數字才有意義,原本的 `{ y: 150 }` 已經蓋不到新的 `y: 334`。

**2. 兩個帶正負號的 MP/CR 視窗會裁掉符號。**
`gainedMp`(52px)與 `deltaCrMpLayout`(46px)只容得下符號加兩位數,所以 `+173`
讀回 `"173"`。對「增加」而言 parse 後數值相同,問題被掩蓋;但**三位數的「減少」
會掉掉負號,以相反的正負號寫進資料庫**。兩者都已加寬到符號加三位數。

這兩個缺陷都由 `pnpm vision:check-ocr-numbers` 固定住:它斷言**解碼後的數值**
而不只是「有讀到東西」——漂移到相鄰列的視窗照樣會讀到一個數字,只是錯的那個。

### 6.3 尚未解決的時序脆弱點

結算畫面上,`score_system` 標籤第一次被辨識到的那一格,`result` 橫幅也同時超過門檻
並結束該場對戰。也就是說 **BP/MP 的 OCR 一場只有一次機會**,失敗就永久遺失
(`ranked-no-numbers` 診斷會記錄,但數值救不回來)。本次錄影中那一次剛好成功,
但游標剛好停在數字上、或動畫還沒定格,都會讓它失敗。

另外累計 BP 是**逐格遞增的動畫**(實測 88638 → 88754 → 88762),
所以若未來要記錄累計值,必須等它定格,不能取第一格。

## 7. P0/P1 優化落地(2026-08-26 晚)

依 `docs/recognition-optimization-plan.md` 實作:

**P0-2 — OCR 資源重用。** Tesseract worker 改為行程生命週期共用(`stop` 時釋放,
讀取失敗時重建);`recognizeNumber` 改收當前 tick 的 frame 而非檔案路徑,
不再每次重新解碼。實測:worker 冷啟動 278ms、熱讀 25ms —— MP 結算 tick 的
OCR 成本從約 1372ms(4 × 冷啟動+讀取)降到 101ms(4 × 熱讀),
從超出 500ms 預算 2.7 倍變成佔預算 20%。`recognizeBPGain` 併入 `recognizeNumber`。

**P0-1 — OCR 寬限保持。** 最終結算畫面不再在看到的同一 tick 關閉對戰:
結果先寫入,對戰保持開啟(`OCR_RETRY_GRACE_MS` = 5 秒),讓數值 OCR 逐 tick
重試,全部到手或寬限到期才 finalize。`isResultMidDetect` 在寬限期間維持 true,
擋住新對戰誤開。重播的 `--fail-first-ocr N` 注入可驗證重試確實救回數值。

**P1 — 累計值穩定讀取。** `mp` 與 `current_cr`(MP 版面)是逐格遞增動畫,
而 DB 以「讀值 − delta = 賽前值」儲存,抓到動畫起點會**雙重扣除**。
改為連續兩個 tick 讀到相同值才接受;寬限到期仍未定格則取最後一讀(不劣於舊行為)。
delta 欄位(+15 / +124)不是動畫,維持一次即收。

replay 鏡像(`replay-recording.cjs`)已同步全部三項。

## 8. 廣場賽誤判事故與修正(2026-08-27)

**現象**:一場階級對戰被記為 `weekendPlaza`,且 bp/mp/cr 全為 null(DB #330,
witch vs dragon,敗北)。

**歸因(已證實)**:全專案只有一行程式能寫入 `weekendPlaza`
(`plazaDetect.score > 0.7`),所以該探測必然衝過了門檻。三個缺陷疊加:

1. **探測範圍錯誤(根因)**。廣場賽標籤「週末廣場賽」其實只在**結算畫面**出現,
   且與 BP/MP/CR **互斥**。舊實作卻在整場對戰的每個 tick 都探測它 ——
   標籤在對戰中不可能存在,所以**對戰中的每一次命中,依定義都是誤判**。
   它撞的是**畫面上的中文卡片文字**:模板是五個華麗中文字,而戰場滿是華麗中文字。
   實測在某張卡的效果文字上得到 0.5846(位置 1072,118),距門檻僅 0.12,
   而一場對戰約有 1200 個 tick × 640×360 窗口。

2. **單幀即採信**。相鄰的 CPU 探測明確要求連續兩幀,註解寫著這是為了
   「不讓單幀誤判通過」;而範圍大四倍、未校準的 plaza/custom 反而沒有這個保護。

3. **弱訊號永久封鎖強訊號**。命中後設 `shouldModifyMode = false`,
   使結算畫面上已驗證 1.000/0.000 的積分制度標籤**再也無法糾正**模式。
   數值全 null 也源於此路徑,並且因為 `ranked-no-numbers` 診斷是以
   `mode === 'ranked'` 為條件,模式被誤判後**連診斷也一併被消音** ——
   events.jsonl 當天只有一筆 tick-over-budget。

**修正**:

- plaza 移到結算畫面,作為積分制度標籤的**互斥替代**(`scoreSystem === null` 時才探測),
  並升為 `authoritative`。對戰期間完全不再探測。
- 引入模式訊號**信賴分級**(`authoritative` > `strong` > `weak`):
  弱訊號只在無更佳資訊時採用,且永不阻止結算畫面的權威訊號糾正。
  取代原本的 `shouldModifyMode` 布林閂鎖。
- plaza 要求**連續兩幀且位置穩定**(容差 8px)。卡片文字會移動,UI 標籤不會 ——
  這是目前唯一能區分兩者的低成本判據(沒有 plaza 素材可校準 ROI)。
- custom 同樣加上連續兩幀要求。
- `ranked-no-numbers` 改以**是否看到積分制度標籤**為條件,不再依賴最終 mode 欄位:
  標籤是「數值本該存在」的證據,mode 是可能出錯的結論。
- 新增診斷 `weak-mode-accepted`(附畫面)與 `mode-corrected`,
  讓未校準探測的每次採信與每次糾正都留下證據。

**副作用**:兩個半畫面搜尋不再跑滿整場對戰,而是在模式確立後就停止 —— tick 成本下降。

**尚未解決**:plaza 的 ROI 仍未校準(`topRight` 640×360),因為沒有任何廣場賽素材。
取得素材後應收窄 ROI 並加入 `check-rois` / `check-scales`。

### 8.1 廣場賽 ROI 校準(2026-08-27)

### 8.2 自訂房 ROI 校準(2026-08-27)

**素材來源**:專案擁有者自行錄製的 1280×720 視窗化自訂房對戰(4:16,敗北),
已納入 `tests/fixtures/captures/custom-1280-windowed-lose/`。

`custom` 是最後兩個半畫面搜尋(`leftHalf` / `rightHalf`),而且是整個 tick 裡
最貴的一段 —— **3.19 G 乘加,佔 78%**。收窄它同時解掉效能與誤判兩個問題。

**量測結果**(512 格 @2fps,其中 39 格顯示房間畫面,跨三次進出):

| 項目           | 值                                             |
| -------------- | ---------------------------------------------- |
| `host` 位置    | (75, 97) —— 逐像素不動                          |
| `guest` 位置   | (1158, 97) —— 逐像素不動                        |
| 淡入位移極值   | (45, 97) / (1187, 97),垂直到 y=84              |
| 真實命中分數   | 0.899–0.958                                    |

面板淡入時整組往外滑,所以出現一格的大幅外擴;視窗涵蓋整段位移加 20px 邊界。
兩側都比對整組模板 —— 哪一邊顯示 `室長` 取決於使用者是不是房主。

**收窄前後**(模板 50×40):

|                            | 舊 `leftHalf`/`rightHalf` | 新 `customOwn`/`customOther` |
| -------------------------- | ------------------------- | ---------------------------- |
| 視窗                       | 640×720 ×2                | 119×93 ×2                    |
| 每 tick 乘加數             | 3.19 G                    | 30.1 M(**1/106**)           |
| 實測耗時                   | 136.7 ms                  | 2.5 ms                       |
| 真實命中最高分             | 0.958                     | 0.958(不變)                 |
| 最差誤判(598 格負樣本)    | **0.7002**                | **0.5066**                   |

**這是一個已經上線的誤判,不是理論風險。** 50×40 的標籤掃過 640×720 的戰場,
必然會撞到長得像它的卡圖:

- 房間淡出格,卡圖在 (857, 144) 得到 **0.7002**,門檻正是 0.7;
- 一般對戰中,卡圖在 (430, 339) 得到 0.6916,且**連續五格**在 0.689 以上。

判定條件是連續兩格超過門檻,所以差 0.009 就會把一場普通對戰整場記成 `custom`。
同一個卡圖熱點在 `cpu-practice-1920-fullscreen` 也出現(0.6236),並非單一錄影的巧合。

**順帶確認的行為**:自訂房打完只有 `result_mid` = gameset(0.904),
**不會出現 win/lose 橫幅**,接著直接回房間。模式判定其實是靠戰後回到房間的那段
(結算後 1.5 秒,落在 `RESULT_MODE_GRACE_MS` 15 秒內)觸發 —— 收窄 ROI 必須涵蓋
那段畫面,否則自訂房會完全無法辨識。

**後續**:至此 `leftHalf` / `rightHalf` / `topRight` 三個半畫面視窗全部沒有呼叫者,
已從 ROI 表移除。每一個被校準掉的半畫面搜尋,結果都同時是「tick 裡最貴的一段」
和「誤判來源」;要加新探針時請先量測位置,不要再引入這種視窗。

### 8.3 重播橫幅 ROI 校準(2026-08-27)

**素材來源**:專案擁有者自行錄製的 1280×720 視窗化重播操作(1:41,兩次播放,
第二次提前離開),已納入 `tests/fixtures/captures/history-1280-windowed/`。

這是 ROI 表裡最後一個全畫面搜尋。但收窄它主要不是效能問題,**是正確性問題**。

**重播畫面跟真實對戰完全相同** —— 同樣的 VS 畫面、先後攻覆蓋層、戰場、`gameset`
橫幅。沒有任何下游邏輯分得出來,唯一的防線就是抓到播放開始的「開始播放對戰紀錄」
橫幅。而那個橫幅**只在畫面上停留約 1 秒**(500ms tick 下就兩格)。

原本探針每 4 個 tick 跑一次(每 2 秒)。用 2 秒的取樣週期去抓 1 秒的事件會混疊。
實測四個 tick 相位:

| 相位  | 偵測到橫幅 | 記錄的假對戰 |
| ----- | ---------- | ------------ |
| `0.0` | 兩次都漏   | **2 筆**     |
| `0.5` | 兩次都中   | 0            |
| `1.0` | 只中第一次 | 1 筆         |
| `1.5` | 兩次都漏   | **2 筆**     |

**四分之三的相位會產生至少一筆假對戰記錄**,其中一筆寫成 `mode=unknown, result=lose`。

而 4 tick 的取樣頻率不是「判斷這樣就夠」的結果,是被全畫面搜尋的成本逼出來的 ——
成本直接造成了正確性缺陷。

**量測結果**(204 格 @2fps,兩次播放):

| 項目         | 值                               |
| ------------ | -------------------------------- |
| 橫幅位置     | (498, 409) —— 兩次播放都逐像素相同 |
| 真實命中     | 0.822–0.891 @scale 1             |
| 最差誤判     | 0.4025(全片,門檻 0.6)          |

**收窄前後**(模板 290×40,邊界 30px):

|                    | 舊:全畫面 @scale 2 | 新:`ROI.history` @scale 1 |
| ------------------ | ------------------- | -------------------------- |
| 視窗               | 1280×720            | 350×102                    |
| 每次乘加數         | 490 M               | 45 M                       |
| 執行頻率           | 每 4 tick           | **每 tick**                |
| 每 tick 攤提成本   | 123 M               | 45 M(仍便宜 2.7 倍)      |
| 最差誤判(680 格)  | 0.526               | **0.462**                  |

改成每 tick 後四個相位全部 0 筆假記錄。`history` 也因此從 `SCALE` 表移除 ——
它原本是唯一沒有正樣本可驗證縮放安全性的集合,現在有了,而且校準視窗在
scale 1 已經夠便宜。

**已知的剩餘缺口**:橫幅只武裝一個 15 秒盲區計時器,而計時器不知道重播是否還在播。
重播長於 15 秒時冷卻會在播放中途到期(本錄影第一次播放橫幅 0:06、冷卻到 0:21、
播放到 0:58,中間 37 秒無保護,純粹靠 VS 畫面剛好落在冷卻內);提前離開時冷卻又
還在跑(離開 1:23.5、冷卻到 1:29),期間開的真實對戰會被吃掉。兩個方向都會錯。

正解是把計時器換成閂鎖:播放期間有持續的 UI chrome(右下暫停鍵、底部
`X 播放‧停止`,真實對戰底部是 `Tab 戰場紀錄 / F 額外PP / Space 回合結束`),
chrome 在就鎖、消失就解。但 chrome **在 VS 畫面上不存在**,所以閂鎖仍要由橫幅起始。
需要新增辨識模板,尚未實作。

**至此 ROI 表已無任何廣域視窗。**

### 8.4 重播播放 chrome —— 用閂鎖取代盲區計時器(2026-08-27)

8.3 把橫幅偵測修好了,但橫幅只武裝一個 15 秒盲區計時器,而計時器不知道重播是否還在播。
**沒有任何長度是對的**:

- 太短 → 重播活得比它久。1280 素材實測:橫幅 0:06、計時器 0:21 到期、播放到 0:58
  —— **33 秒毫無保護**。
- 太長 → 提前離開後計時器還在跑,期間開的真實對戰會被靜靜吃掉。

**新增模板** `resources/templates/replay_chrome/playstop.png`(118×20):播放列上的
`X 播放‧停止` 按鍵提示。從正規化畫布(`normalizedToPng()`)上裁切,幾何與 ROI 表同一座標系。

| 訊號 | 回答什麼 | 在畫面上多久 | 作用 |
| ------ | ---------------- | ---------- | ------------------------------ |
| 橫幅 | 重播**開始了** | 約 1 秒 | 設底線 15 秒,撐到 chrome 出現 |
| chrome | 重播**還在播** | 整段播放 | 頂住閂鎖,消失後 2 秒釋放 |

**兩個都必要。** chrome 在 VS 畫面上還沒出現(橫幅→chrome 空窗實測 1280 = 10.5s、
1920 = 10.0s,而 VS 畫面正好落在裡面),所以閂鎖必須由橫幅起始;橫幅一秒就沒,
所以延續必須交給 chrome。`REPLAY_BANNER_FLOOR_MS = 15_000` 正是為了跨過那個空窗。

**為什麼不用 `Esc 選單`**:它位置固定、看起來更好用,但重播以外的選單畫面也有它。
閂鎖在選單被觸發會**反過來壓掉真實對戰** —— 這是使用者永遠不會發現的失敗方向。
`X 播放‧停止` 是重播專屬:真實對戰底部是 戰場紀錄 / 額外PP / 回合結束,沒有播放控制。

**量測結果**:

| 素材 | 命中 | 分數 | 位置 |
| ---------------- | ---- | ----------- | ------------------ |
| 1280 視窗化重播 | 87 格 | 0.797–1.000 | x = 141 / 200 / 336 |
| 1920 全螢幕重播 | 14 格 | 0.889–0.980 | x = 199 |
| 667 格負樣本 | **0** | 最差 0.407 | —— |

底部列靠左對齊且項目會增減(`Tab 戰場紀錄` 時有時無),chip 因此水平位移 135px。
視窗涵蓋三個位置加 20px 邊界,並在畫布底緣截斷 —— 列就貼在螢幕最下方,下面沒有空間。

**實際行為**(`vision:replay-history`):

```
[00:06.0] replay detected (banner 0.862, chrome 0.095) - suppressing
[00:54.0] replay ended - resuming        <- chrome 最後 0:52.5,+2s
[01:14.0] replay detected (banner 0.852, chrome 0.111) - suppressing
[01:33.5] replay ended - resuming        <- 使用者 1:32 離開,1.5s 後釋放
```

保護範圍從固定 15 秒變成**跟著重播實際長度走**;釋放從固定 15 秒變成**離開後 2 秒內**。

**tick 結構的改變**:原本在冷卻期間會在 tick 最上方直接 return,連畫格都不載入。
現在必須載入畫格才能讓 chrome 探針把閂鎖頂住,所以閂鎖期間每 tick 多花約 18ms
(載入 15ms ＋ 兩個探針 3ms)。重播不常見,而且那是 500ms 預算的 3.6%。

**尚未驗證**:重播被**暫停**時 chrome 是否仍在(按鍵提示理應不受影響,但沒有素材)。
若暫停會讓 chrome 消失,閂鎖會在 2 秒後釋放 —— 但暫停畫面不會產生 VS 畫面或結算,
所以不會造成誤記錄,最多是暫停期間失去保護。

### 8.5 模板品質稽核(2026-08-27)

#### modes_cpu —— 分離度 0.0285,已修正

正是職業紋章,所以分數是「CPU 牌組是哪個職業」的函數,其他職業從未量測過。

#### play_order —— 試過重切,**結論是不要改**

`second` 一致地比 `first` 低約 0.11(三支錄影:0.740/0.740/0.727 對 0.853/0.853/0.835),
看起來像個該修的目標。從真實畫面重切之後,真實命中確實大幅上升 —— 但**分離度反而下降**。

| 版本 | 最弱真實命中 | 最差誤判 | 分離度 |
| ---------- | ------------ | -------- | ---------- |
| **出貨版** | 0.6128 | **0.4013** | **0.2115** |
| 全幅重切 | **0.7251** | 0.5499 | 0.1752 |
| 字形緊裁 | 0.6187 | 0.5600 | 0.0587 |

(1038 格、5 支錄影;用命中位置區分真偽 —— 覆蓋層是逐像素固定的。)

**原因**:出貨模板的去背區域存的是接近純黑的 RGB,而 `to_gray_opencv` 直接丟棄 alpha
用存下來的 RGB。那片平坦的黑幾乎不跟任何東西相關,等於一個柔性遮罩,分數因此主要由
字形決定。從真實畫面重切會把**背景結構**一起帶進模板,於是它跟戰場上任何相似紋理都
更相關 —— 最差誤判就出現在一張純星雲背景的戰鬥畫面上(0.401 → 0.550)。

**推論**:「從正規化畫布重切一定比較好」這個規則是錯的。它對 `cpu_prebattle` 和
`replay_chrome` 有效,是因為那兩個元素本來就坐在**平坦的深色底**上(牌組面板、快捷列),
重切帶進來的背景本身就接近平坦。字形浮在**有紋理的美術**上時,平坦的假背景反而更好。
