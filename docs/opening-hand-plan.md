## 動機

現在一場對局記錄的是「誰對誰、先後手、勝負、模式、分數」。牌組匯入之後，Analyzer 知道那 40
張牌是什麼（`DeckCard`），卻不知道**這一場實際抽到了什麼**。起手手牌是牌組調整時最常被問的
問題（這張留不留、換幾張、後手起手三費以上幾張），而它剛好是整場對局裡唯一「位置固定、時間
充裕、可以慢慢看」的一個畫面。

本計畫**不實作卡片層級的勝率分析**。`docs/deck-import-plan.md` 已經把那劃為另一個計畫，這裡
維持同一條界線：本計畫只負責讓資料存在且可信。

## 決定性的限制：一張卡有很多種插畫

畫面上的一張卡與 portal 給的那張圖，可能不是同一張圖。三種版本破壞的東西不同：

| 版本            | 畫面上差什麼                             | 破壞什麼                              |
| --------------- | ---------------------------------------- | ------------------------------------- |
| 閃卡 / premium  | 同一張插畫，加上動態光澤、粒子、框飾特效 | 破壞**單幀**像素比對；幾何沒變        |
| 替代插畫        | 整張圖不一樣                             | 插畫比對**必然失敗**，無法補救        |
| 語言 / 稀有度框 | 名稱文字、框飾                           | 只影響拿卡框當特徵的做法              |

而 `card_details.<id>.common` 只有一個 `card_image_hash` 與一個 `card_banner_image_hash`
（`tests/fixtures/deck-import/witch-pool.json`），**沒有任何列舉版本的欄位**。所以「把所有版本
的卡圖抓下來建索引」這條路沒有資料來源——這不是準確度問題，是資料上不存在。

**這一節在 2026-09-10 被量測修正了一半。** 官方那唯一一張圖對上畫面的**預設插畫**時分離度極好
（正確 0.669–0.872，錯誤最高 0.427），所以插畫**就是**主判準；上表列的三種版本不是「插畫不能
用」的證據，而是**它的失效邊界**：

- 閃卡：同一張插畫加上動態光澤，幾何沒變，靠多幀取最佳與去均值 NCC 應該撐得住——**未量測**。
- 替代插畫：官方資料裡沒有它，所以第一次遇到一定認不出來。只能靠「認出來之後把當下的裁圖存成
  觀測樣本」補，下一次才會命中。
- 語系與稀有度框：只影響拿卡框或卡名當特徵的做法，插畫區不受影響。

換句話說，版本問題決定的不是「用不用插畫」，而是「**要不要做觀測樣本那套機制**」。

## 辨識架構

> 2026-09-10 重寫。初版把「卡面數字」放在第一層、插畫比對放在最後當 tiebreak。實測之後**兩者
> 對調**：數字讀不出來，插畫比對乾淨得不必猶豫。量測數字見下一節。

三層，第一層做掉幾乎所有工作：

1. **候選集限縮**：`my_deckId` 的 `DeckCard`，unique 卡約 25~30 張。退化順序是
   「預設牌組 → 該職業卡池 + 中立 → 放棄並記為不明」。2Pick 直接落到第二層。
   這一層是**猜測**（使用者可能用了非預設牌組），所以下面每一層都必須能說「這張不在候選集裡」，
   而不是硬塞一個最接近的。
2. **主判準：插畫比對**。官方卡圖裁到固定比例的插畫區，對上畫面上那張卡的插畫窗，做去均值 NCC。
   實測 63 張候選、8 個已知身分的畫面裁圖：**8/8 命中，正確分數 0.669–0.872，496 次錯誤配對
   最高 0.427**。門檻用「第一名與第二名的差距」而不是絕對分數。
3. **Tiebreak：卡名 OCR 或卡面數字**，只在第 2 層的勝差不足時才跑。注意數字這條路本身很弱
   （見下節），所以它是「有勝差爭議時的第二意見」，不是保底。

### 什麼時候讀

**只在幾何穩定的幀讀。** 面板會做進場動畫，卡片還在縮放定位時所有 ROI 都會偏——實測偏了近
20px，足以讓插畫窗切到隔壁。判斷方式：費用徽章是一個亮圓盤，很好偵測，穩定幀上一律落在
`x0+7, y0+21`（±2px，跨四份錄影與八幀）。偵測到的圓心離期望值太遠 = 這幀還在動，跳過。

**以徽章為錨。** 找到圓盤之後，插畫窗、卡名條、攻防徽章全部相對它定位，就能吸收幾像素的漂移。

### 參考指紋在哪裡算

**不要在 host 用 sharp/jimp 算。** 那條 pipeline 與 frame 的灰階／縮放不一致，比對會系統性
偏掉。新增一個 stdin 指令 `indexCards { cards: [{ cardId, path }] }`，由引擎用它自己的
`to_gray_opencv` / `downscale` 算，結果寫進 `CardArtSample`，開機不重算，換演算法時用
`algoVersion` 整批失效。

### 替代插畫的長尾：讓它自己學

一旦某張卡被確定，就把當下的裁圖指紋存成該 `cardId` 的 `source='observed'` 樣本。下一次同一個
替代插畫出現就直接命中。這是唯一能覆蓋「官方沒告訴你的版本」的辦法，而且它是本機觀測資料、
不散布素材，與卡圖快取同一套立場。需要每張卡的樣本數上限。

## 階段 2 的可行性量測（2026-09-10）

全部用既有錄影做的，樣本是五份錄影裡有正確答案的換牌畫面。

### 卡面數字：不可行

20 個已知答案的費用徽章，四種方法：

| 方法                                  | 命中      |
| ------------------------------------- | --------- |
| tesseract，引擎現用的二值化門檻 128   | **1/20**  |
| tesseract，門檻調到 210（最佳）       | 9/20      |
| 摳出字形後最近鄰比對                  | 12/20     |
| 原始灰階 NCC                          | 7/20      |

原因是這個表面和結算畫面完全不同：**費用是半透明亮圓盤上的 ~28px 數字**。二值化到 128 整個
圓盤變白、把數字吃掉；門檻拉高數字出得來，但圓盤邊框的弧線黏在數字旁邊，OCR 就讀成別的。
暗場景的樣本直接碎掉。

**所以初版計畫裡「費用本來就能用現成的 `ReadNumber` seam 讀」這句話是錯的**，那個 seam 是為
結算畫面上「深底白字、字大」的數字調的。

### 插畫比對：可行，而且分離度很大

先驗證畫面對畫面（同一張卡出現在不同錄影裡）：

| 比對                                   | 分數           |
| -------------------------------------- | -------------- |
| 同一張卡，不同錄影、不同解析度         | 0.949、0.974   |
| 不同卡（46 組）                        | 最高 0.434     |

再驗證真正要用的方向——**官方卡圖對畫面**。官方圖是完整卡片（530×687，含卡框），畫面上的卡
裁得更緊，所以整卡對齊只有 0.346；改成**只對齊插畫區**（官方圖的 x 0.140–0.853、
y 0.198–0.837）之後：

| 項目                                   | 結果                        |
| -------------------------------------- | --------------------------- |
| 候選集                                 | 63 張（比一副牌的 unique 還多） |
| 命中                                   | **8/8**                     |
| 正確配對分數                           | 0.669–0.872                 |
| 496 次錯誤配對                         | 最高 0.427，99 百分位 0.300 |
| 最小勝差（第一名 − 第二名）            | **+0.389**                  |

### 這份量測沒有涵蓋的

- **閃卡與替代插畫**：五份錄影都是同一位使用者、都是預設插畫。長尾仍然只能靠觀測樣本。
- 只有一種語系、四張不同的卡、八個裁圖。插畫區的比例是在**一張卡**上擬合出來的，實作時要用
  多張重新求，並且改成以徽章為錨而不是固定偏移。
- 官方卡圖需要先下載到本機快取才有得比。新使用者第一次跑的冷啟動要有答案（見卡圖託管那節）。

## 候選集：從牌組改成職業卡池（2026-09-13）

實機第一次跑之後改的。那一場（match 367）**面板讀到了**——八列俱全、`swapped` 全 0——
但**沒有任何一張卡被認出來**，而 `indexCards cards=17` / `cardsIndexed indexed=17 failed=0`
證明建索引的管線完全正常。原因是候選集只有預設牌組的 17 張，而使用者打的是別副牌。

使用者的判斷是對的：**「設定的牌組」不能當唯一標準，忘記切牌組是常態不是例外。**
而且更糟——那台機器有 19 副 witch 牌組，加起來只有 17 張 unique 卡，因為其中 18 副是
沒有卡表的舊牌組（只有名字與職業）。所以「放寬到同職業所有牌組」也救不了。

### 量測：放大到整個職業卡池會不會過大？

抓了完整的一個職業卡池（175 張，含中立，實測 92MB 圖），對五份錄影重跑：

| | 63 張候選 | 175 張（整個職業＋中立） |
| --- | --- | --- |
| 認出來的格子 | 8 / 12 | **12 / 12** |
| 正確卡的分數 | 0.872–0.996 | **逐位數完全相同** |
| 最小勝差 | 0.505 | 0.456（門檻 0.30） |
| 四格辨識成本 | 0.483ms | 1.363ms |

**候選變多不會降低正確卡的分數**，只會讓勝差略縮——實測最多掉 0.05，離門檻還有 1.5 倍。
那四格原本認不出來的，正是卡不在小候選集裡；放大之後分數 0.907–0.992。

所以**放大不是風險，是修正**。真正的代價是下載量：一個職業 175 張 ≈ 92MB。

### 決定

- **候選集 = 該職業的卡池 + 中立**，與牌組完全脫鉤（`store.class_fingerprints`）。
- **建索引的範圍 = 使用者實際會打的職業**：從 `Match.my_class` 與 `Deck.class` 推得。
  只打一個職業的人下載一份 92MB，不是七份。**最近打過的職業排最前面**，同職業內牌組裡的
  卡優先——它們最可能出現在下一手。
- **一次跑完，不分次。** 初版每次啟動只抓 60 張，結果是一個卡池要開三次 app 才能用，中間
  那幾次功能靜靜地什麼都不做。**那比下載久更糟：使用者分不出它跟壞掉有什麼差別。**
  改成把缺的全部抓完，5 個並行、每 25 張送一批給引擎——邊跑邊變準，中途關掉也留得住。
- **職業對應表不複製到 Rust**。`Card.class` 是 portal 的數字 id，順序和本專案的職業名不同
  （主教與夜魔對調），`deckImport.ts` 的 `CLASS_ID_TO_NAME` 是唯一真相。所以改成**建索引時就
  把職業名標在指紋上**（`016_add_card_art_class.sql`），引擎只比字串。複製一份表最糟的地方
  不是會錯，是錯了不會有任何東西壞掉——對局只會安靜地跟錯職業的卡比對。

### 認不出來時，要看得出是哪一種

`cardId` 是 NULL 有三種原因，要採取的行動完全不同：候選集是空的（沒建索引）、最高分約 0.5
（打的牌不在這個職業的池裡，理論上不該發生）、最高分接近門檻（門檻或畫面有問題）。
所以 `fingerprint::name` 現在**連拒絕都帶著數字回來**，機器在回報時記
`opening-no-candidates` 或 `opening-unnamed` 旗標，並附上候選數與最高分的診斷。

## 資料模型

**已落地**：`resources/migrations/014_add_opening_hand.sql`，內容如下。`CardArtSample` 沒有
一起建——它屬於階段 2 的插畫比對，而階段 0 第 4 題還沒答，先不要為還沒決定要做的事建表。

> 實際落地的檔案裡每個欄位都有註解，這裡只留形狀。

```sql
-- ---------- MatchOpeningCard ----------
-- 一列一張卡，不是八個欄位：之後要問的是「起手有 X 的勝率」，那是 join，不是欄位掃描。
CREATE TABLE IF NOT EXISTS MatchOpeningCard (
  matchId    INTEGER NOT NULL,
  stage      TEXT    NOT NULL,  -- 'pre' | 'post'
  slot       INTEGER NOT NULL,  -- 0..3
  cardId     INTEGER,           -- NULL = 認不出來，這是合法狀態
  confidence REAL,
  swapped    INTEGER,           -- 只有 pre 列有意義：這張被選中換掉了嗎
  decidedBy  TEXT,              -- 'numeric' | 'name' | 'art-portal' | 'art-observed'

  PRIMARY KEY (matchId, stage, slot),
  FOREIGN KEY(matchId) REFERENCES Match(id) ON DELETE CASCADE
);

-- ---------- CardArtSample ----------
CREATE TABLE IF NOT EXISTS CardArtSample (
  cardId      INTEGER NOT NULL,
  source      TEXT    NOT NULL,  -- 'portal' | 'observed'
  algoVersion INTEGER NOT NULL,
  vector      BLOB    NOT NULL,
  seenAt      DATETIME NOT NULL,

  PRIMARY KEY (cardId, source, algoVersion, seenAt)
);

CREATE INDEX IF NOT EXISTS idx_openingcard_cardId ON MatchOpeningCard(cardId);
```

理由與慣例：

- **`cardId` 不設 FK 到 `Card`**，與 `DeckCard`、`CardPool` 一致：`Card` 是別人資料的快取，會被
  清掉或換語言重抓。這裡該退化成「卡號 10573310，詳情不明」，不是壞掉。
- **`matchId` 用 CASCADE，且只掛在 `Match` 上。** 不碰 Deck 家族——`ON DELETE SET NULL` 會觸發
  既有 trigger（見牌組版本化的那個坑）。
- **`decidedBy` 不是裝飾。** 上線初期一定會問「這批資料能不能拿來算勝率」，而只有這個欄位能
  回答。同理 `confidence` 是調門檻用的。
- `Match` 上另加一個 `openingRecognized`（或以「四列齊全且 cardId 皆非 NULL」推導），讓統計能
  排除只認出兩張的對局。兩者選一，別兩套並存。

## 狀態機的位置

換牌畫面在先後手覆蓋層之後，也就是 `MatchStarted` 已發出、`Phase::InBattle` 剛開始的那幾秒。
照 `phase.rs` 的紀律，**這是 InBattle 底下的一段等待，不是新的頂層 phase**（那個模組開頭就在
講「pre-battle 模式偵測不是一個 phase，只是帶 TTL 的資料」）。

- 新增兩個字樣 probe 加進 `PROBES`：`CHANGE`（只在換前出現）與 KEEP 列的字樣或等待字樣
  （換前換後都在）。兩者的組合就是狀態：兩個都在 = 換前，只有後者 = 換後（等待對手）。
  只有它們夠強時才讀格子，其餘 tick 完全不付錢。
- 用 `accumulate.rs` 穩定八個格子的空／滿與內容。換後最短只有 1.50s（3 tick），共識要能接受
  只有 2 幀。
- `CHANGE` 字樣消失的那一刻 = 換前定稿；接下來的等待狀態讀換後，用同一組 KEEP ROI。
- 結果透過 `MatchUpdated` 的 patch 送出，與 mode / bp 走同一條路，不另開事件種類。

**Q1 位置是否 pixel-stable — 是。** KEEP 四格的水平範圍（canvas 座標，跨錄影變異 ≤2px）：

| 2    | 400 – 551  | 152 |

**Q2 被換掉的卡怎麼標記 — 不是標記，是位移。** 選中的卡從 KEEP 列**實際移動**到 CHANGE 列，

**效能。** 在 settled 面板幀上逐段量測（中位數，30 次）：

| 段落                                   | 修正前  | 修正後  |
| -------------------------------------- | ------- | ------- |
| `card::locate`（四張）                 | 3.8–4.0ms | 0.15–0.17ms |
| `of_screen_art` ×4                     | 0.09ms  | 0.11ms  |
| `identify` ×4 對 63 張                 | 0.50ms  | 0.54ms  |
| 卡片路徑合計                           | ≈4.4ms  | ≈0.8ms  |
| `mulligan::read`（每幀）               | 1.15–1.30ms | 不變 |
| 整個 `reading::read`                   | 45–47ms | 41–46ms |

`find_badge` 原本每個候選中心走 49×49 個像素、441 個候選、每格一次，改成每列做前綴和、圓盤與外環
各是一段列區間的差；**同一組像素、同一組整數和、分數逐位元相同**，門檻不必重量，測試以舊寫法
當 oracle 比對。沒改 `Fingerprint::similarity` 的重複算均值（4×63 次合計 0.5ms）與 `of_screen_art`
的配置（0.1ms）——量了，太小，不值得動。`identify_panel` 仍然每一幀 settled 都跑：現在那正是投票
的材料，而且只剩 0.8ms。

另外 `fingerprint::identify` 現在把同一 `cardId` 的多個樣本當一張卡（取最高分），第二名必須是
**別張卡**。今天的候選集一張卡一列，但 `CardArtSample` 的 `observed` 來源一落地就會有同卡多列，
屆時沒有這條規則的話那張卡會永遠以勝差 0 被拒。
