# 計畫：換牌建議（對上某職業該留哪幾張）

> 這份文件回答的是「要把這件事做好，該怎麼做」。它取代了
> `docs/meta-stats-plan.md`「候選功能：起手牌與留牌勝率」那一節裡關於**桶的形狀**的
> 結論——那個形狀會讓最好的版本永遠做不出來，原因見下面〈為什麼我上一版的桶是錯的〉。

## 一、產品問題，以及為什麼最直覺的答案是錯的

要回答的是一個**決策**：發到 `{a,b,c,d}`、對手是龍族、我先攻，該換掉哪幾張。

完整的答案是 `E[勝 | 保留集合 S, 手牌 H, 情境]`，而 40 張抽 4 張有九萬種手牌、每手有
16 種保留集合——那個表永遠填不滿。所有人（17Lands、HSReplay、Firestone、Mobalytics）
都做同一個化約：**逐張卡看**。我們也只能這樣，但化約之後要問對問題。

### 三個看起來很像、其實不同的問題

| 問題 | 估計量 | 乾淨嗎 |
| --- | --- | --- |
| A. 手上**有**這張卡，好不好？ | 發到勝率 − 沒發到勝率 | **乾淨**（發牌是隨機分派） |
| B. 母體多常**留**這張卡？ | 保留率 | **乾淨**（純描述，不是估計） |
| C. **留**這張卡，好不好？ | 留下勝率 − 換掉勝率 | **不乾淨**，見下 |

我們要的是 C，而市面上所有產品拿 B 的分子去算 C 然後不說。

**A 不能代替 C。** 這點我之前講得不夠清楚：A 是 intent-to-treat，它已經**包含**了玩家
後續怎麼處理那張卡。一張八費的結束牌可能「有它不吃虧」（A 為正——因為你會把它換掉），
但「留著它」是災難。A 回答「這張卡在牌組裡值不值得」，**不回答換牌決策**。

**C 被兩層混淆污染：**

1. **手牌其餘三張。** 你只在其他牌不錯的時候留它，所以「留下時勝率高」反映的是其他三張。
   （HearthPwn 上那個經典案例：某卡 Mulligan WR 最高、Played WR 最低，保留率只有 20%。）
2. **玩家本人。** 強的玩家既留得對、也贏得多。跨使用者彙總會把「會留這張的人比較強」
   讀成「留這張比較強」。

## 二、把兩層混淆都拿掉的設計

這是這份文件的核心，也是唯一值得寫一份新計畫的理由。

### 2.1 對第一層：條件化在「其餘三張」

**我們看得到整手牌。** 這是我們相對於所有競品的結構性優勢——它們的資料裡只有
「X 有沒有在最終手牌裡」，我們有發牌當下的四張、以及哪幾張被換掉。

其餘三張是**隨機發的、在決策之前**，所以條件化在它們身上是合法的（那是 pre-treatment
covariate，不是 post-treatment）。在同一組「其餘三張長得差不多」的手牌裡比較留與換，
第一層混淆就消失了。

完整條件化（其餘三張的確切身分）會讓分層爆炸，所以用一個**便宜的摘要**：其餘三張的
平均費用，分成三段（低 / 中 / 高）。那抓到的正是主要的混淆——**你在其餘手牌曲線漂亮的
時候才敢留貴的**。

### 2.2 對第二層：技術——原本要做固定效果，**已放棄**

原本的設計是 install 內的固定效果：只用「同一個人、同一個分層、有時留有時換」的觀測，
玩家層級的一切在差分裡消掉。理論上乾淨，**實務上在這個規模是過度工程**，2026-09-17 的
市場研究把它否掉了，理由有三個，每一個單獨都夠：

1. **它會把資料削掉九成，而且是退化成空集不是退化成無調整。** 只有 switchers 進入估計：
   同一個玩家、同一張牌、可比較的其餘三張、而且真的有時留有時換。117 個安裝下，
   一格能留下的 cluster 是個位數。**一個在資料不足時回傳「沒有」而不是「比較粗」的估計式，
   在產品上是壞的。**
2. **Yang (2018, arXiv:1803.05484) 那套去技術偏誤的方法要求 `games ≫ players²`。**
   我們 players ≈ 117。
3. **技術根本不是這個題目的主要混淆。** 這點是我原本想錯的方向：所有**被實際記錄下來的**
   mulligan 統計失效案例——HearthPwn 的 Prince Liam（72% Mulligan WR / 21% keep rate）、
   Blizzard 論壇那串、Out of Games 的教學——講的全是「**手牌其餘部分**」與 win-more，
   **沒有一個是「只有高手才留」**。同一個 archetype 內，高手和一般人的 keep 決策重疊度很高。
   Yang 的 Pyramids 案例是策略偏好差異極大的桌遊，不是這個。

**所以第二層改成兩件便宜的事：**

- **薄格子往上一層收縮**，不是不給：`(職業, 對手, 先後手, 卡, 分層)` 樣本不足時，
  依序退回 `(職業, 對手, 卡)` → `(職業, 卡)`，用 Beta-binomial shrinkage，
  **並且在畫面上講明它退了哪一層**。這是 HSGuru 作者在論壇上叫使用者手動做的事
  （「改看 archetype 層」），我們自動做並標示。
- **技術若要控制，用協變量不用固定效果**：把玩家自己的整體勝率分成三段，當成桶的一個維度
  （mtgds 2022 對 17Lands 資料就是把 player win rate 當協變量）。**這個先不做**——它多一個
  維度、讓格子更稀疏，而且多洩漏一點個人資訊。等量夠了再說。

### 2.3 固定效果留在本機，而且那裡它是免費的

**本機只有一個玩家，所以「我留 X 時 vs 我換 X 時」本來就是 within-player 對照。**
不需要任何固定效果機制，混淆自動消失——這是這個 app 相對於所有雲端產品的結構優勢，
而我原本把它當成雲端功能的附屬品。**本機版是主功能，雲端聚合是補充。**

本機版剩下的混淆只有「其餘三張」，而那正好是 2.1 處理的，也只需要本機資料就能做。

## 三、為什麼我上一版的桶是錯的

`docs/meta-stats-plan.md` 寫的是：

```
(date, my_class, oppo_class, card_id, kept, result) -> count
```

**它把「其餘三張」丟掉了。** 一旦這樣上傳，2.1 的條件化就永遠做不到——資料裡沒有那個
資訊，而且補不回來。這是那種「上線兩年後才發現當初少存了一欄」的錯誤。

### 修正後的桶

```
(date, tier, my_class, oppo_class, play_order, card_id, kept, rest_cost_band, result) -> count
```

多的是 `rest_cost_band`（其餘三張的平均費用，3 段）與 `play_order`。

### 列數：我上一則算錯了，而且算多了

我寫「約 140 列／安裝／天」，那是把 key 變寬當成列數變多。**不會。**
一天打 20 場 = 80 個「卡片 × 場次」觀測，**不管 key 多寬，去重後的列數都不會超過 80**。
key 變寬只是讓合併變少。

| | 每個安裝每天 |
| --- | --- |
| 現有的 `buckets` | 約 15 |
| 起手桶（上限就是觀測數） | **≤ 80** |

117 個安裝 ≈ 每天 9,400 列；D1 免費額度 10 萬／天。**1,200 個安裝左右開始逼近**，
之後走 `docs/account-sync-plan.md` 的 R2。`content_hash` 的跳過機制照用。

### 為什麼不上傳「整手」一列

一場一列（四個 card_id + 四個 kept 旗標 + 結果）**列數更少**（20 列／天），資訊更完整。
被否決的原因只有一個，而它夠重：**一手四張加結果加日期，接近一個指紋。** 桶是計數，
還原不出任何一場對局；整手列可以。**在這個取捨上選隱私，即使它同時比較貴。**

## 四、估計流程

```
輸入：起手桶，tier = 'clean'
格子：(my_class M, oppo_class C, play_order P, card X, rest_cost_band s)

對每格：n_keep, w_keep, n_swap, w_swap
        d = w_keep/n_keep − w_swap/n_swap
        兩側都要有觀測；缺一側就往上退一層

退階（thin cell fallback）：
        (M, C, P, X, s)  →  (M, C, X)  →  (M, X)
        每一階都用 Beta-binomial 往上一階收縮
        **畫面上必須寫出它退到哪一階**

per-install 上限：沿用現有的 10，避免一個磨同一對位的人主導那格
k-匿名：每格至少 5 個貢獻的 install
```

三件必須沿用既有規則的事：

- **只有 `clean` tier**（`rollup.ts` 的 `classifyRow`）。手改過、有辨識警告的不進。
- **只有四張全辨識的 pre 手牌**能產生桶——少一張就不知道「其餘三張」是什麼。
- **每個百分比旁邊都有 n**，這一頁和起手頁、環境頁同一條規則。

### 保留率要和勝率並列，不是附註

HSReplay、Firestone、Mobalytics 三家共識，而且 HearthPwn 那串裡讀者就是靠它解謎的
（21% 的保留率解釋了 72% 的勝率）。對我們還多一層意義：**保留率直接說明這一格有多少
swapped 對照組**——保留率 95% 的卡，它的「換掉」那一側幾乎是空的，估計自然不可信。

**定義寫死：分母是「被發到的次數」，不是「mulligan 後在手的比例」。** Firestone 在自己的
產品裡把這兩個搞混過（issue #342），這是個真的會踩到的坑。

## 五、永遠修不掉的三件事，要寫在畫面上

1. **辨識缺漏不是隨機的。** 替代插畫／閃卡系統性認不出來，那些手牌整手被排除。
   一萬個使用者只會讓一個有偏的估計的區間變窄。`dealRateSuspect` 那個警報是目前唯一
   會出聲的機制，它要繼續存在。
2. **沒有段位，而且已經放棄用固定效果去補。** 上傳不含段位與 MP。跨玩家的技術差異
   在雲端版是**沒有被控制的**（見 2.2），只有本機版因為只有一個玩家而自動免疫。
   「高分段的人怎麼換」這個問題不存在，而且雲端的數字要當成「所有使用這個 app 的人
   平均起來的行為與結果」，不是「正確答案」。
3. **手牌內的交互作用。** 「有 B 的時候才留 A」是真實存在的策略，而逐張卡的化約看不到它。
   分層在其餘三張的**費用**上抓到一部分，抓不到具體組合。這是化約的代價，要說。

## 六、這個功能該長在哪裡：HUD，不是統計頁

**市場研究最重要的一條，而我原本的計畫完全漏掉了。**

真正有 mulligan 建議的產品只有兩家——**HDT（HSReplay 資料）** 與 **Firestone**——
而兩家都是**在換牌的當下，用 overlay 疊在遊戲畫面上**。HDT 的做法是每張牌上一個
1–4 的名次徽章，hover 才出數字；側欄可以改成按 Mulligan WR 排序。網站上的表格是拿來
事後研究的，**不是使用者實際做決定時看的東西**。

這個 app 已經有 HUD（`src/renderer/src/hud.tsx`），而引擎在換牌畫面**已經認得出那四張牌**
——那正是這整個功能的資料來源。也就是說，「在換牌當下把建議畫在畫面上」所需要的辨識
能力**已經完成了**，缺的只是把答案送到 HUD。

換牌只有十幾二十秒，**讀得快比算得準更決定這個功能有沒有用**。所以：

- **主要介面是 HUD**：四張牌各一個名次或一個「留／換」傾向，數字收在次要位置。
- **統計頁是次要的**，給事後研究與檢查樣本用。
- 名次比百分比快——這是 HDT 的選擇，而且他們後來的版本更往那個方向走。

## 七、一個必須知道的市場訊號：HSReplay 放棄了用勝率回答這件事

2026-03，HSReplay 推出 **Mulligan G-V2**，它**不再預測勝率**，改預測
「**高手在這個具體的四張手牌／牌組／對手職業／先後手下，會不會留這張**」——
一個行為模仿模型，條件化在整手牌上（所以它處理得了 synergy、重複牌、費用曲線）。

這是這個領域唯一一次可觀察到的方法論轉向，而且方向很清楚：**市場領導者認為「用勝率
回答換牌問題」做不起來，於是改去模仿高手。**

對我們的意涵：

- **我們沒有高手樣本可模仿**（沒有段位資料），所以模仿那條路走不了。走因果修正這條路
  是對的，**但要接受在這個規模下它只能做到「有對照組的收縮估計」，不是乾淨的因果效應。**
  這句話要寫進 UI 的說明，比寫進估計式重要。
- G-V2 有一個互動值得偷：**使用者點選要留哪張之後，其餘牌的建議會依「已留的牌」重算**。
  我們的估計本來就條件化在其餘三張上，這個互動幾乎是免費附送的。

## 八、階段

| 階段 | 內容 | 相依 |
| --- | --- | --- |
| **M5** | **本機層：你自己的「留 vs 換」對照**，條件化在其餘三張。純本機、無上傳、無同意問題 | 無，**先做這個** |
| **M6** | HUD：換牌當下把 M5 的答案畫在四張牌上 | M5 |
| **M0** | client 端起手桶 + 純函式測試。不碰網路 | 無 |
| **M1** | 獨立的、預設關閉的同意選項。**不是把現有開關的涵蓋變大** | 無 |
| **M2** | 伺服器 migration + ingest（沿用 `content_hash` 跳過） | M0 |
| **M3** | 估計與退階 + `/v1/mulligan`，含 k-匿名與 per-install 上限 | M2 |
| **M4** | 雲端層併進 HUD 與統計頁，標明資料來源與退到哪一階 | M3 |

**順序改了。** 原本 M5 是最後的附屬品，現在它是第一個——因為本機版**沒有技術混淆**
（只有一個玩家）、**不需要同意**、**不受 J-4 阻擋**，而且它回答的正是那個核心問題。
它唯一的弱點是樣本，而那正好是雲端要補的。

**M1 是硬閘門。** 現有開關徵求的是計數桶的同意；這是每一場的卡片清單彙總後的計數，
性質不同，必須重新問。

**J-4（Cygames 服務條款）仍未定案**，它擋的是 M2 之後的一切，但**擋不到 M5 與 M6**。
