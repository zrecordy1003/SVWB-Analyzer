# 計畫：換牌建議（對上某職業該留哪幾張）

> 這份文件回答的是「要把這件事做好，該怎麼做」。它取代了
> `docs/meta-stats-plan.md`「候選功能：起手牌與留牌勝率」那一節裡關於**桶的形狀**的
> 結論——那個形狀會讓最好的版本永遠做不出來，原因見下面〈為什麼我上一版的桶是錯的〉。

## 一、產品問題，以及為什麼最直覺的答案是錯的

要回答的是一個**決策**：發到 `{a,b,c,d}`、對手是龍族、我先攻，該換掉哪幾張。

完整的答案是 `E[勝 | 保留集合 S, 手牌 H, 情境]`，而 40 張抽 4 張有九萬種手牌、每手有
16 種保留集合——那個表永遠填不滿。所有人（17Lands、HSReplay、Firestone、Mobalytics）
都做同一個化約：**逐張卡看**。我們也只能這樣，但化約之後要問對問題。

### 三個看起來很像、其實不同的問題

| 問題 | 估計量 | 乾淨嗎 |
| --- | --- | --- |
| A. 手上**有**這張卡，好不好？ | 發到勝率 − 沒發到勝率 | **乾淨**（發牌是隨機分派） |
| B. 母體多常**留**這張卡？ | 保留率 | **乾淨**（純描述，不是估計） |
| C. **留**這張卡，好不好？ | 留下勝率 − 換掉勝率 | **不乾淨**，見下 |

我們要的是 C，而市面上所有產品拿 B 的分子去算 C 然後不說。

**A 不能代替 C。** 這點我之前講得不夠清楚：A 是 intent-to-treat，它已經**包含**了玩家
後續怎麼處理那張卡。一張八費的結束牌可能「有它不吃虧」（A 為正——因為你會把它換掉），
但「留著它」是災難。A 回答「這張卡在牌組裡值不值得」，**不回答換牌決策**。

**C 被兩層混淆污染：**

1. **手牌其餘三張。** 你只在其他牌不錯的時候留它，所以「留下時勝率高」反映的是其他三張。
   （HearthPwn 上那個經典案例：某卡 Mulligan WR 最高、Played WR 最低，保留率只有 20%。）
2. **玩家本人。** 強的玩家既留得對、也贏得多。跨使用者彙總會把「會留這張的人比較強」
   讀成「留這張比較強」。

## 二、把兩層混淆都拿掉的設計

這是這份文件的核心，也是唯一值得寫一份新計畫的理由。

### 2.1 對第一層：條件化在「其餘三張」

**我們看得到整手牌。** 這是我們相對於所有競品的結構性優勢——它們的資料裡只有
「X 有沒有在最終手牌裡」，我們有發牌當下的四張、以及哪幾張被換掉。

其餘三張是**隨機發的、在決策之前**，所以條件化在它們身上是合法的（那是 pre-treatment
covariate，不是 post-treatment）。在同一組「其餘三張長得差不多」的手牌裡比較留與換，
第一層混淆就消失了。

完整條件化（其餘三張的確切身分）會讓分層爆炸，所以用一個**便宜的摘要**：其餘三張的
平均費用，分成三段（低 / 中 / 高）。那抓到的正是主要的混淆——**你在其餘手牌曲線漂亮的
時候才敢留貴的**。

### 2.2 對第二層：install 內的固定效果

`install_id` 在伺服器的每一列原始桶上（`0001_init.sql`），而 `/v1/meta` 已經在做
`GROUP BY install_id, ...` 再彙總。**所以「只在同一個安裝內部做比較」是現成可行的。**

只用「**同一個人、同一個對位、同一個手牌分層，有時留有時換**」的那些觀測。玩家層級的
一切——技術、段位、牌組、心情——在差分裡被消掉。

剩下的變異是什麼？同一個人面對條件相近的手牌，這次留、下次換。那接近**任意的**，
也就是接近隨機分派。這是這個設計能宣稱因果的依據。

### 2.3 一個漂亮的性質，和一個真的限制

**只有「有時留有時換」的人（switchers）會進入估計。** 這聽起來像缺點，但方向是對的：

- 一張所有人都留的卡 → 沒有變異 → 估不出來。**但那張卡也不需要建議。**
- 一張大家意見分歧的卡 → 變異最大 → 估得最準。**而那正是使用者會去查的那張。**

**估計量的力量最強的地方，剛好就是決策最難的地方。**

真的限制要講明：這個估計適用的是「會猶豫的那群人」，不是全體。一張你從來不換的卡，
這個功能對你沒有話可說——它會誠實地說「沒有足夠的分歧可以比較」，而不是編一個數字。

## 三、為什麼我上一版的桶是錯的

`docs/meta-stats-plan.md` 寫的是：

```
(date, my_class, oppo_class, card_id, kept, result) -> count
```

**它把「其餘三張」丟掉了。** 一旦這樣上傳，2.1 的條件化就永遠做不到——資料裡沒有那個
資訊，而且補不回來。這是那種「上線兩年後才發現當初少存了一欄」的錯誤。

### 修正後的桶

```
(date, tier, my_class, oppo_class, play_order, card_id, kept, rest_cost_band, result) -> count
```

多的是 `rest_cost_band`（其餘三張的平均費用，3 段）與 `play_order`。

### 列數：我上一則算錯了，而且算多了

我寫「約 140 列／安裝／天」，那是把 key 變寬當成列數變多。**不會。**
一天打 20 場 = 80 個「卡片 × 場次」觀測，**不管 key 多寬，去重後的列數都不會超過 80**。
key 變寬只是讓合併變少。

| | 每個安裝每天 |
| --- | --- |
| 現有的 `buckets` | 約 15 |
| 起手桶（上限就是觀測數） | **≤ 80** |

117 個安裝 ≈ 每天 9,400 列；D1 免費額度 10 萬／天。**1,200 個安裝左右開始逼近**，
之後走 `docs/account-sync-plan.md` 的 R2。`content_hash` 的跳過機制照用。

### 為什麼不上傳「整手」一列

一場一列（四個 card_id + 四個 kept 旗標 + 結果）**列數更少**（20 列／天），資訊更完整。
被否決的原因只有一個，而它夠重：**一手四張加結果加日期，接近一個指紋。** 桶是計數，
還原不出任何一場對局；整手列可以。**在這個取捨上選隱私，即使它同時比較貴。**

## 四、估計流程（伺服器端）

```
輸入：起手桶，tier = 'clean'
篩選：my_class = M, oppo_class = C, play_order = P
分層：s ∈ {低, 中, 高}（rest_cost_band）

對每個 install i、每個分層 s：
    n_keep[i,s], w_keep[i,s], n_swap[i,s], w_swap[i,s]
    只有 n_keep > 0 且 n_swap > 0 的 (i,s) 進入估計      ← switchers
    d[i,s] = w_keep/n_keep − w_swap/n_swap

彙總：以 (i,s) 的有效樣本數加權平均
收縮：往 0 收縮（`src/shared/stats.ts` 的 shrink）
區間：對加權平均做 bootstrap 或 delta method
發布：k-匿名——每個 (M,C,P,card) 至少 5 個貢獻的 install
```

三件必須沿用既有規則的事：

- **每個 install 每格設上限**（現在是 10），否則一個磨同一個對位的人會主導那一格。
- **只有 `clean` tier**（`rollup.ts` 的 `classifyRow`）。手改過、有辨識警告的不進。
- **只有四張全辨識的 pre 手牌**能產生桶——少一張就不知道「其餘三張」是什麼。

## 五、永遠修不掉的三件事，要寫在畫面上

1. **辨識缺漏不是隨機的。** 替代插畫／閃卡系統性認不出來，那些手牌整手被排除。
   一萬個使用者只會讓一個有偏的估計的區間變窄。`dealRateSuspect` 那個警報是目前唯一
   會出聲的機制，它要繼續存在。
2. **沒有段位。** 上傳不含段位與 MP，所以跨玩家的技術差異只能靠固定效果消掉（install 內），
   不能分層（install 間）。「高分段的人怎麼換」這個問題不存在。
3. **手牌內的交互作用。** 「有 B 的時候才留 A」是真實存在的策略，而逐張卡的化約看不到它。
   分層在其餘三張的**費用**上抓到一部分，抓不到具體組合。這是化約的代價，要說。

## 六、階段

| 階段 | 內容 | 相依 |
| --- | --- | --- |
| **M0** | client 端起手桶 + 純函式測試。不碰網路。 | 無 |
| **M1** | 獨立的、預設關閉的同意選項。**不是把現有開關的涵蓋變大。** | 無 |
| **M2** | 伺服器 migration + ingest（沿用 `content_hash` 跳過） | M0 |
| **M3** | 估計流程 + `/v1/mulligan`，含 k-匿名與 per-install 上限 | M2 |
| **M4** | 頁面：選對手職業 → 一張卡一列的建議，附樣本數與區間 | M3 |
| **M5** | 本機層：**你自己**對上各職業的保留率（純描述，不需要伺服器） | 無，可先做 |

**M5 可以現在就做**，它不需要任何上傳，也是唯一在你自己的資料上就成立的東西：
「你對上龍族時，這七張各留了幾次」。它回答的是「我對這張卡的處理一致嗎」。

**M1 是硬閘門。** 現有開關徵求的是計數桶的同意；這是每一場的卡片清單彙總後的計數，
性質不同，必須重新問。

**J-4（Cygames 服務條款）仍未定案**，它擋的是 M2 之後的一切。
